# 지식 벡터 검색: 채팅에 가까운 지식만 넣기

작성일: 2026-11-19 · 상태: 사용자 결정(2026-11-19), 규칙 문서 변경은 이 PR에서 Leo 승인

## 의도

신입 채팅은 질문할 때마다 신입이 볼 수 있는 게시 지식을 **전부** 프롬프트에 넣는다(`assistant_tools.search_knowledge`). 첫 설계(2026-11-17)는 지식이 적다고 보고 "벡터 DB 없음"을 골랐다. 그런데 지식은 늘어나도록 만들어져 있다.

- 신입이 "담당자에게 등록 요청"을 보내면 담당자가 지식으로 답한다.
- 규정 문서 하나로 Q&A 초안을 최대 10개 만든다.

지식이 수백 건이 되면 질문당 입력 비용과 첫 글자 시간이 지식 양에 비례해 늘어난다. 관련 없는 지식이 섞일수록 근거를 고르는 정확도도 떨어진다(운영 전 점검 I4).

이미 규정 조항에 쓰는 pgvector 검색을 지식에도 적용한다. 질문과 가까운 지식만 넣는다.

## 사용자 결정 (2026-11-19)

- 운영 배포(v 태그) **전에** 넣는다.
- 질문마다 넣는 가까운 지식은 **20건**이다. 시드 신입이 보는 게시 지식이 30건이므로, 데모에서도 실제로 걸러지고 평가로 품질을 확인할 수 있다.
- 임베딩은 **저장할 때 바로** 계산한다. 신입 쪽에는 반영 지연이 없어야 한다.

## 목표

1. 채팅은 질문과 가까운 게시 지식 20건을 넣는다. 질문 임베딩은 조항 검색과 함께 한 번만 한다.
2. 임베딩이 없거나 낡은 게시 지식은 검색 결과와 관계없이 함께 넣는다. 임베딩이 늦거나 실패해도 답에서 지식이 빠지지 않는다.
3. 담당자가 지식을 게시하거나 고치면 그 지식이 곧바로 임베딩된다. 웹의 저장 흐름은 바뀌지 않는다.
4. 질문 임베딩이 실패하거나 시간을 넘기면 지금처럼 지식을 전부 넣는다.

## 비목표

- 유사도 하한(가까운 정도가 낮은 지식 빼기)
- 재순위, 키워드 혼합 검색
- 초안 지식의 임베딩. 게시할 때 임베딩한다.
- 지식 초안 에이전트(`knowledge_draft.py`)의 기존 지식 조회 방식 변경
- 화면 변경

## 실패 조건

- 초안이나 다른 팀, 다른 조직의 지식이 채팅에 들어간다.
- 임베딩이 없거나 실패해서 게시 지식이 채팅에서 빠진다.
- 본문을 고친 지식이 예전 본문의 임베딩으로 검색된다.
- 에이전트가 지식 본문이나 상태를 쓴다.
- 관리 범위 밖 사용자(신입, 다른 팀 교육 담당자)가 지식 임베딩을 쓴다.
- 질문당 비용이 지식 수에 비례해 커진다.

## 접근 방식

| 결정 | 선택 | 다른 안과 기각 이유 |
|---|---|---|
| 임베딩 저장 위치 | **별도 테이블 `knowledge_embeddings`** | `knowledge_items` 칼럼: 웹이 `select('*')`로 읽어(`knowledge.ts`) S10이 지식마다 숫자 1536개를 받는다. 지식 테이블의 update 권한(authenticated 전체)도 손대야 한다. |
| 낡은 임베딩 판정 | **`content_hash`** | 트리거로 지우기: 저장 중에 담당자가 고치면 예전 벡터가 남는 경쟁 상태가 생긴다. 행 잠금이 필요하다. 해시는 저장할 때의 본문을 기록하고, 조회할 때 현재 본문과 비교하므로 경쟁 상태가 생기지 않는다. 쓰기 경로 7곳(웹 save·setStatus, RPC 3개, 시드, 초기화)도 고치지 않는다. |
| 임베딩 계산 시점 | **저장 직후 웹이 `POST /knowledge/index` 호출** | 정기 배치: 새 지식은 다음 실행까지 임베딩 없이 전부 들어간다. 운영 환경 워크플로는 승인이 필요하고 OpenAI 키도 없다. |
| index 요청 형식 | **본문 없는 "빠진 것 채우기"** | 지식 id 지정: 쓰기 경로마다 id를 넘겨야 한다. 빠진 것 채우기는 여러 번 불러도 결과가 같고, 실패하면 다음 호출이 복구한다. |
| 한도 | **새 한도 없음** | 빠진 임베딩만 계산하므로 반복 호출은 OpenAI를 부르지 않는다. 계산량은 담당자가 실제로 저장한 횟수에 묶인다. |
| 시드·초기화 | **백필 스크립트(환경별 1회) + 자연 복구** | 마이그레이션에서 임베딩: SQL은 임베딩을 계산할 수 없다. 초기화 직후에는 임베딩이 없어 전부 들어간다(지금과 같은 동작). 스크립트나 담당자의 다음 저장이 채운다. |

## 데이터 (마이그레이션 `0014_knowledge_embeddings.sql`, 추가만)

**테이블 `knowledge_embeddings`**
- 칼럼
  - `knowledge_id`: pk, `knowledge_items` 참조, on delete cascade
  - `org_id`
  - `content_hash`: 임베딩한 본문의 `md5(question || E'\n' || answer)`
  - `embedding vector(1536)`
  - `created_at`
- HNSW 코사인 인덱스를 둔다(`document_clauses`와 같음).
- 해시가 현재 본문과 같을 때만 "임베딩 있음"으로 본다. category와 status는 해시에 넣지 않는다. 바뀌어도 다시 임베딩하지 않는다.

**RLS와 권한**
- 읽기: 그 지식을 읽을 수 있으면 임베딩도 읽는다(`knowledge_items`를 `exists`로 조회해 지식 RLS를 물려받는다). 신입은 초안이나 다른 팀 지식의 임베딩을 볼 수 없다.
- 쓰기: authenticated에는 select만 준다. 먼저 `revoke all`로 기본 권한을 지운다. 쓰기는 저장 RPC로만 한다. anon에는 권한이 없다.
- Realtime publication에는 넣지 않는다.

**RPC**
- `knowledge_without_embedding(p_org uuid default null)` (security invoker)
  - 해시가 일치하는 임베딩이 없는 **게시** 지식을 돌려준다. 반환은 id, question, answer, 오래된 순 100건이다.
  - 대상 범위
    - 일반 호출: 호출자의 관리 범위(`private.can_manage_scope`). ops_staff는 회사 공통, team_trainer는 자기 팀이다.
    - service_role: `p_org`가 주어지면 그 조직만 본다.
- `save_knowledge_embeddings(p_items jsonb)` (security definer)
  - 입력: `[{id, question, answer, embedding}]`, 1~100개. 이 범위를 벗어나면 22023이다.
  - 함수 안에서 조직과 관리 범위를 검사한다.
    - 다른 조직이거나 없는 지식이면 건너뛴다.
    - 관리 범위 밖이면 42501이다.
    - service_role은 이 검사를 생략한다(`replace_document_clauses`와 같음).
  - `org_id`는 지식 행에서 가져온다. `content_hash`는 **받은 본문**으로 계산한다. 그 사이 본문이 바뀌었다면 해시가 맞지 않아 다음 index 호출에서 다시 계산된다.
  - upsert하고 저장한 개수를 돌려준다.
- `match_knowledge(p_embedding vector(1536), p_count int default 20)` (security invoker, `hnsw.iterative_scan = strict_order`)
  - 해시가 일치하는 게시 지식을 가까운 순으로 `p_count`건 가져온다. 개수는 1~50으로 제한하고, null이면 20이다.
  - 여기에 임베딩이 없는 게시 지식을 더한다.
  - 반환: id, category, question, answer, similarity(임베딩 없는 지식은 null). similarity 내림차순으로 정렬한다.
  - 범위는 호출자의 RLS가 정한다. 신입에게는 게시된 회사 공통 지식과 내 팀 지식만 보인다.

**pgTAP `10_knowledge_embeddings.sql`**
- 검색 범위: 신입 기준으로 초안, 다른 팀, 다른 조직 지식은 빠진다. 임베딩 없는 게시 지식은 항상 들어간다. 결과는 가까운 순서이고 개수는 상한·하한을 지킨다.
- 해시: 본문을 고치면 "임베딩 없음"으로 바뀐다. 상태나 분류를 바꿔도 그대로다. 지식을 지우면 cascade로 함께 지워진다.
- 저장 RPC 권한: 신입과 범위 밖 담당자는 42501, 입력 경계는 22023이다. service_role 경로도 확인한다.
- 권한: anon은 실행할 수 없다. authenticated는 테이블에 쓸 수 없다.

## 에이전트 (`services/agent`)

**`app/knowledge_index.py`**
- `index_missing(client, embed_fn) -> int`: 빠진 지식 조회 → 임베딩 → 저장 RPC. 라우트와 백필 스크립트가 함께 쓴다.
- 임베딩 입력은 `question\nanswer`의 앞부분 2000자다. 해시는 자르지 않은 본문으로 계산한다.
- DB 호출은 스레드로 돌린다. 진행 중인 채팅 스트림을 막지 않기 위해서다.

**`POST /knowledge/index`**
- 대상: team_trainer, ops_staff. 한도: 없음
- 요청 본문은 `{}`다. 담당자 토큰으로 `index_missing`을 실행한다.
- 응답은 200 `{embedded:int}`이고, 임베딩이나 DB 오류는 502다. 로그에는 예외 이름만 남긴다.

**채팅(`assistant.py`)**
- 질문 임베딩(직전 사용자 질문 포함)을 한 번 하고 `match_knowledge`(20건)와 `search_documents`(6건)를 동시에 부른다. 과제 조회는 이와 병렬로 돈다.
- 질문 임베딩이 실패하거나 시간 제한(현재 조항 검색의 4초)을 넘기면 `search_knowledge`로 지식을 전부 넣고 조항은 넣지 않는다.
  - 지금도 조회 전체가 질문 임베딩을 기다리므로 첫 글자 시간은 늘지 않는다.
  - 프롬프트는 짧아진다.
- 참고 자료 순서를 **과제 → 지식 → 조항**으로 바꾼다. 지식도 이제 질문마다 바뀌므로, 고정된 과제가 앞에 있어야 프롬프트 캐시가 맞는다.
- 지시문의 지식 설명을 "질문과 가까운 게시된 사내 지식"으로 고친다. "질문과 관계없는 지식이 섞여 있을 수 있다"는 문장도 넣는다.

**백필 `scripts/index_knowledge.py`**
- service_client로 `index_missing`을 반복한다. `--org`의 기본값은 데모 조직이다.
- 한 회차에 저장한 것이 0건이거나 최대 반복 수에 이르면 끝낸다.
- 환경마다 마이그레이션 뒤에 한 번 실행한다. 초기화 뒤에는 선택이다.

## 웹 (`apps/web`)

- S10 지식 동작(`useKnowledgeActions`의 save, setStatus, resolve)이 성공하면 `POST /knowledge/index`를 백그라운드로 부른다.
  - 결과를 기다리지 않고 실패는 무시한다. 임베딩이 없는 지식도 채팅에 들어가기 때문이다.
  - 다만 `agentFetch`는 401을 받으면 로그아웃하므로, 백그라운드 호출에도 같은 동작이 적용된다.
- 문서 초안 저장(`save_knowledge_drafts`)은 초안만 만들므로 index를 부르지 않는다.
- 화면 문구와 배치는 바뀌지 않는다.

## 시드, 평가, 운영

- 로컬, 스테이징, 운영 각각 마이그레이션 뒤에 `index_knowledge.py`를 한 번 실행한다(`docs/deploy.md`).
- 임베딩 모델을 바꾸면 조항처럼 지식 임베딩도 다시 만들어야 한다. `knowledge_embeddings`를 비우고 백필을 다시 돌린다.
- `eval_assistant.py` 8문항이 변경 전과 같이 통과해야 한다. 실행 순서에 백필을 넣는다. 넣지 않으면 "전부 넣기" 경로만 측정된다.
- 시드 지식 30건의 질문을 표현만 바꿔 물었을 때 그 지식이 20건 안에 드는지 한 번 확인하고, 결과를 PR에 적는다.
- 스테이징에서 PR #61 방식으로 입력 토큰과 첫 글자 시간을 비교한다.
