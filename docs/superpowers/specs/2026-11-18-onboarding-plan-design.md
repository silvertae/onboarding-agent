# 온보딩 플랜 관리 설계 (단계·과제 템플릿·한 사람 추가)

작성일: 2026-11-18 · 상태: Leo 승인(지금 구조 넓히기, 할당 방식 C, 진행 중 신입에게는 넣지 않음, 사용 중 템플릿 제한, 심사 전 필수·단계 관리는 제외). 구현 계획: `docs/superpowers/plans/2026-11-18-onboarding-plan.md`
근거: `docs/superpowers/specs/2026-11-17-onboarding-agent-design.md`의 과제 31개 고정 구조를 넓힌다. 참고: Workday Onboarding Plans(입사일 기준 스테이지, 관리자 작성·매니저 개인화).

## 1. 의도

지금 과제 템플릿 31개와 단계 3개(입사일·첫 주·첫 달)는 마이그레이션에 고정돼 있어서, 과제를 바꾸려면 개발자가 배포해야 한다. 실제 도입하면 팀마다 교육 과제가 다르고 회사 규정과 단계 구분도 회사마다 다르다.

**인사(경영지원) 담당자와 팀 교육 담당자가 온보딩 과제를 직접 만들고, 신입에게 자동으로 할당되게 하고, 필요하면 한 사람에게만 과제를 더 주며, 진행 현황을 관리한다.** 심사 전에 시연 흐름까지 갖춘다. 조직별 단계 관리는 다음 단계로 미룬다(5.1).

## 2. 목표 / 비목표 / 실패 조건

**목표**
1. 기본 과제 관리: 교육 담당자는 우리 팀, 경영지원 담당자는 우리 부서의 과제 템플릿을 추가·수정·보관한다. 보관한 템플릿은 새 신입에게 들어가지 않는다.
2. 자동 할당: 신입 온보딩을 시작하면 그 시점의 회사 공통(부서) 과제 + 그 팀 과제 중 보관되지 않은 것이 들어간다(지금 `_start_onboarding`과 같은 흐름).
3. 한 사람만 추가: 담당자가 특정 신입에게만 과제를 하나 추가한다. 그 과제는 기본 목록에 보이지 않고 다른 신입에게 들어가지 않는다.
4. 진행 중인 신입 보호: 기본 목록에 과제를 추가하거나 보관해도 이미 시작한 신입의 과제 목록은 바뀌지 않는다.
5. 사용 중인 템플릿은 제목·안내문만 고칠 수 있다.
6. 데모 초기화가 템플릿도 시드 상태로 되돌린다.
7. 시연 흐름: 팀 과제 추가 → 새 신입에게 자동 할당 → 한 사람만 추가 → 사용 중 잠금 → 초기화.

**비목표**
조직별 단계 관리(단계 테이블·관리 탭, 다음 단계), 입사 전 단계(음수 일수), 직무·경력별로 다른 플랜(대상 조건), 입력 양식 과제(`input`) 편집기, 다른 부서·팀 과제를 선행으로 묶기, 템플릿 버전 관리·변경 이력 화면, 템플릿 삭제, 진행 중 신입에게 일괄 반영, 단계별 알림, 과제 순서 끌어 놓기(정렬은 기한·생성순).

**실패 조건 (동작해도 실패)**
- 담당자가 다른 부서·팀의 템플릿을 만들거나 고친다. 신입이 템플릿을 고친다.
- 템플릿을 고쳤더니 이미 진행 중인 신입의 과제가 잠기거나, 제출할 수 없게 되거나, 다른 단계로 옮겨진다.
- 한 사람에게 추가한 과제가 다른 신입에게 보이거나 들어간다.
- 과제 상태가 RPC 밖에서 바뀐다.

## 3. 제약

- 마이그레이션은 추가만 한다. `task_templates.stage`(enum)와 `due_offset_days`는 지우거나 이름을 바꾸지 않는다.
- 상태 변경 규칙(`submit_task`, `confirm_task`, 트리거의 선행 잠금 해제)은 템플릿 행을 실시간으로 읽는다. 그래서 진행 중인 신입이 가리키는 템플릿의 "구조"를 바꾸면 그 신입의 진행이 바뀐다(목표 5와 충돌).
- 템플릿 코드는 조직 안에서 유일하고(`unique(org_id, code)`), 선행 관계와 에이전트 근거 표시가 코드를 쓴다.
- UI는 `.interface-design/system.md`를 따르고, 새 화면·큰 변경은 시안을 먼저 만들어 Leo 확인을 받는다.
- S12 과제 서식(`task_template_files`, `task-forms` 버킷)은 문서만 있고 아직 구현 전이다. 서식 영역을 같은 화면에 함께 만든다.

## 4. 접근 방식

| 방식 | 내용 | 장단점 |
|---|---|---|
| **A. 지금 구조 넓히기 (선택)** | 조직별 단계 테이블, 템플릿 편집 RPC, 한 사람용 숨은 템플릿 | 상태 규칙·화면·에이전트가 거의 그대로. 조직당 단계 목록은 하나 |
| B. Workday식 플랜 엔터티 | 플랜마다 대상 조건·단계·과제 목록, 신입은 맞는 플랜을 받음 | 직무별 온보딩 가능. 시작 함수·권한·타임라인을 다시 짜야 하고, 공통+팀이 섞이는 지금 구조와 맞추기 어려움 |
| C. 단계는 개발자가 관리 | enum 값 추가 마이그레이션 + 템플릿 편집만 | 가장 빠름. "회사마다 단계가 다르다"를 화면에서 못 풂 |

Leo가 A를 골랐다. 할당 방식은 C(기본 목록 자동 + 한 사람만 추가)를 골랐다. 직무별 플랜이 필요해지면 A의 단계·템플릿 위에 플랜 묶음을 더해 B로 간다.

## 5. 결정된 구조

### 5.1 단계 (이번에는 그대로)

- 단계는 지금 enum(`day1`·`week1`·`month1`)을 그대로 쓴다. 단계 시작일은 0·5·30일.
- 템플릿 편집 화면은 "단계"와 "단계 시작 후 N일"(0~60)을 받고, `due_offset_days = 단계 시작일 + N`으로 저장한다. 새 컬럼은 없다.
- 조직별 단계 관리(단계 테이블, 관리자 탭, 타임라인·에이전트가 단계 목록을 읽기)는 심사 뒤 다음 단계에서 한다. 그때 템플릿에 단계 참조 컬럼을 더하고 enum은 남긴다.

### 5.2 과제 템플릿 편집

- 새 컬럼: `task_templates.archived_at timestamptz`, `task_templates.assigned_to uuid null`(한 사람용, 5.3), `task_templates.created_by uuid null`, `task_templates.is_seed boolean default false`(기존 31개는 true).
- 담당 범위: `team_trainer`는 `team_id = 내 팀`, `ops_staff`는 `department = 내 부서`. 관리자는 템플릿을 편집하지 않는다.
- 모든 쓰기는 RPC로만 한다(테이블 쓰기 정책 없음): `save_task_template`, `archive_task_template`, `restore_task_template`, `add_task_for_hire`.
- **만들 수 있는 종류**: `read`(읽을 내용), `ops`·`practice`(안내 + 완료/제출), `setup`(체크리스트 항목 1~20개), `assessment`(교육 담당자만, 일정·결과는 나중에 기록). `input`은 기존 시드만 쓰고 새로 만들지 않는다.
- **편집 칸**: 제목(1~60자), 안내문(0~2000자), 단계, 기한(단계 시작 + 0~60일), 완료 방식(`self`·`confirm`·`staff_only`), 해당 없음 허용, 체크리스트(setup), 선행 과제(같은 담당 범위의 보관되지 않은 기본 과제 중 0~3개, 자기 자신·순환 불가).
- **사용 중 잠금**: 어떤 신입에게든 들어간 템플릿(`task_instances`가 있는 템플릿)은 제목과 안내문만 고칠 수 있다. 종류·완료 방식·단계·기한·체크리스트·선행·해당 없음 허용은 잠기고, 바꾸려면 "보관 후 새로 만들기"를 안내한다. 이렇게 해야 진행 중인 신입의 제출·확인·잠금 해제가 그대로 유지된다(제약 2). 제목·안내문 수정은 진행 중인 신입에게도 바로 보인다(오탈자 수정 용도).
- **코드 자동 부여**: 새 템플릿 코드는 `<접두어>-<번호>`. 접두어는 부서면 `HR`·`GA`·`AC`, 팀이면 `teams.task_code_prefix`(새 컬럼, AI팀 시드 `AI`, 없으면 `TM`). 번호는 같은 접두어의 가장 큰 번호 + 1(두 자리 이상). 한 사람용은 `<접두어>-P<번호>`.
- 정렬: `sort_order`는 새 템플릿에 같은 단계의 가장 큰 값 + 10을 준다.

### 5.3 한 사람만 추가

- `add_task_for_hire(p_new_hire, …편집 칸)`: 숨은 템플릿(`assigned_to = 신입`)을 만들고 그 신입에게 과제 인스턴스를 바로 만든다. 선행 과제는 고를 수 없다(바로 `todo`). 기한은 신입 입사일 + `due_offset_days`, 단 오늘보다 이르면 오늘.
- 호출자는 그 신입을 담당해야 한다: 교육 담당자는 같은 팀 신입, 경영지원은 조직의 신입 누구나(지금 조회 권한과 같음). 과제의 담당은 호출자의 팀 또는 부서.
- `_start_onboarding`과 기본 목록 화면은 `assigned_to is not null`인 템플릿을 제외한다. 보관된 템플릿도 제외한다.
- 한 사람용 과제를 빼려면 지금처럼 "해당 없음(사유 필수)"을 쓴다. 지우지 않는다.
- 한 사람용 과제의 서식 올리기 화면은 이번 범위 밖이다.

### 5.4 화면

- **S12 → "온보딩 과제" `/tasks`**(메뉴 이름 변경): 왼쪽 과제 목록(단계별 묶음, 보관 보기 전환), 오른쪽 패널에 편집 칸 + 서식(S12의 업로드 영역 그대로) + "보관". 머리 동작 "과제 추가". 사용 중인 과제는 잠긴 칸을 읽기 전용으로 보이고 "N명이 진행 중이라 제목·안내문만 고칠 수 있어요"를 표시한다.
- **S6 신입 상세(교육 담당자)** 와 **S9 부서 업무함(입사자 필터를 고른 상태)**: "이 신입에게 과제 추가" 버튼 → 편집 칸과 같은 대화 상자(선행 칸 없음). 추가된 과제는 목록에 "이 신입만" 배지.
- **S2·S3·S5**: 바뀌지 않는다. 한 사람용 과제도 같은 단계 묶음에 나온다.
- 문구는 구현 계획 Task 4의 표를 `docs/screens.md`에 옮긴다.

### 5.5 에이전트

- 바꾸지 않는다. 단계가 그대로이고, 한 사람용 과제도 신입 본인 과제로 조회된다.
- 한 사람용 템플릿은 RLS로 대상 신입과 담당자에게만 보인다.

### 5.6 데모 초기화

- `reset_demo`가 추가로: 시드 템플릿의 편집 칸을 시드 값으로 되돌리고 보관을 푼다. 시드가 아닌 템플릿은 보관한다(관리자가 만든 신입이 쓰고 있을 수 있어 지우지 않는다). 시드 신입은 지금처럼 다시 시작한다.

## 6. 만드는 사람에게 맡기는 것

RPC 내부 구현과 오류 코드 매핑, 대화 상자·패널의 컴포넌트 구성, 시드 값을 되돌리는 방법(시드 사본 테이블 또는 함수 안 상수), 마이그레이션 파일 나누기, 테스트 픽스처.

## 7. 내가 정한 것 (Leo 확인 필요)

- 경영지원은 세 부서(인사·총무·회계) 모두 자기 부서 과제를 관리한다("인사 담당자"만이 아니라).
- 사용 중인 템플릿은 제목·안내문만 수정, 나머지는 보관 후 새로 만들기.
- 새로 만들 수 있는 종류에서 입력 양식(`input`)은 뺀다. 평가(`assessment`)는 교육 담당자만.
- 선행 과제는 같은 담당 범위 안 기본 과제 중 3개까지. 한 사람용 과제는 선행 없음.
- 템플릿·단계는 지우지 않고 보관만 한다.
- 한 사람용 템플릿은 다른 신입이 볼 수 없게 `task_templates` 조회 정책을 바꾼다.
- 새 과제 코드는 자동(`AI-11`, `GA-09`, 한 사람용 `HR-P01`).
- 서식 영역을 같은 화면(S12 "온보딩 과제")에 함께 만든다.
